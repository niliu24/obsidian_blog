> Linux 物理内存管理采用 **Buddy System** 作为底层页级分配器，管理连续物理页的分配与释放；在其之上，**SLUB** 分配器为内核对象提供高速缓存。二者配合实现从物理页到内核对象的完整内存分配体系。

## 物理内存组织

### NUMA 节点 (Node)

在多处理器系统中，物理内存按 NUMA 节点划分：

```c
// 每个 NUMA 节点对应一个 pglist_data
typedef struct pglist_data {
    struct zone node_zones[MAX_NR_ZONES];  // 内存区
    struct zonelist node_zonelists[MAX_ZONELISTS]; // 分配优先级列表
    int nr_zones;                           // 可用区数量
    unsigned long node_start_pfn;           // 起始物理页号
    unsigned long node_present_pages;       // 物理页总数
    unsigned long node_spanned_pages;       // 总跨度（含空洞）
    int node_id;                            // 节点 ID
    // ...
} pg_data_t;
```

### 内存区 (Zones)

每个 Node 的物理内存划分为多个 Zone，x86_64 典型分区：

| Zone | 名称 | 地址范围 | 用途 |
|------|------|----------|------|
| ZONE_DMA | DMA 区 | 0 ~ 16 MB | 需要 DMA 的低端内存（ISA 设备） |
| ZONE_DMA32 | DMA32 区 | 0 ~ 4 GB | 兼容 32 位 DMA 设备 |
| ZONE_NORMAL | 普通区 | 4 GB ~ 剩余物理内存 | 内核直接映射，最常用 |
| ZONE_HIGHMEM | 高端内存 | （仅 32 位） | 无法直接映射的内存 |

> 在 x86_64 上，ZONE_HIGHMEM 不存在——因为 64 位地址空间直接映射区域足够覆盖所有物理内存。

## Buddy System

Buddy System 是 Linux 最核心的物理页分配器，管理 `struct page` 数组中的所有空闲页。

### 核心算法

将空闲页按 **order**（2^order 个连续页）分组成链表，存储在 `free_area[11]` 数组中（最大 order 为 10，即单次最大分配 2^10 = 1024 页 = 4 MB）：

```
free_area[0] → 2^0 页 (4KB)  链表
free_area[1] → 2^1 页 (8KB)  链表
free_area[2] → 2^2 页 (16KB) 链表
  ...
free_area[10] → 2^10 页 (4MB) 链表
```

### 分配流程 (以 order=2 为例)

```
请求 order=2 (16KB)：
  ┌─ free_area[2] 非空 → 直接取
  └─ free_area[2] 为空 → 向上找 free_area[3] (order=3, 32KB)
       │ 取 32KB 块，分成 2 个 16KB 的 buddy
       │ 一个 16KB 返回给请求者
       └─ 另一个 16KB 插入 free_area[2] 链表
```

### 释放与合并 (Coalescing)

释放时检查其 **buddy**（地址相邻的同 order 块）：

* 若 buddy 空闲 → 合并为 2×order 的块
* 递归向上合并，直到无法继续
* 利用 `struct page` 中的 `_mapcount & PAGE_MAPCOUNT_BUDDY2` 位和 `private` 字段跟踪 order 和是否为 buddy

### 核心数据结构

```c
// mm/page_alloc.c
struct free_area {
    struct list_head  free_list;  // 空闲块链表
    unsigned long     nr_free;    // 该 order 的空闲块数量
};

struct zone {
    // ...
    struct free_area  free_area[MAX_ORDER];  // free_area[0..10]
    unsigned long     *_ptype;   // 页类型标记（可选）
    // ...
};
```

### 关键函数

| 函数 | 说明 |
|------|------|
| `alloc_pages(gfp_mask, order)` | 分配 2^order 个连续物理页，返回 `struct page *` |
| `alloc_page(gfp_mask)` | 分配单页，`alloc_pages(gfp_mask, 0)` 的简写 |
| `__get_free_pages(gfp_mask, order)` | 分配物理页并返回 **虚拟地址** |
| `__get_free_page(gfp_mask)` | 分配单页返回虚拟地址 |
| `get_zeroed_page(gfp_mask)` | 分配已清零的页 |
| `__free_pages(page, order)` | 释放物理页 |
| `free_pages(addr, order)` | 通过虚拟地址释放页 |

### GFP 标志

| 标志 | 含义 |
|------|------|
| `GFP_KERNEL` | 内核常规分配（可能睡眠） |
| `GFP_ATOMIC` | 原子分配（中断上下文，不可睡眠） |
| `GFP_USER` | 用户空间页分配 |
| `GFP_HIGHUSER` | 用户空间（可能从 HIGHMEM 分配） |
| `GFP_DMA` | 从 ZONE_DMA 分配 |
| `__GFP_ZERO` | 分配后清零 |
| `__GFP_HIGHMEM` | 允许从 HIGHMEM 分配 |
| `__GFP_RECLAIM` | 允许内存回收（kswapd + direct reclaim） |

### 代码示例

```c
#include <linux/gfp.h>
#include <linux/mm.h>

// 分配 4 个连续物理页（16KB）
struct page *pages = alloc_pages(GFP_KERNEL, 2);
if (!pages) {
    /* 分配失败 */
    return -ENOMEM;
}

// 获取虚拟地址
void *addr = page_address(pages);
// 使用 addr ...
// 释放
__free_pages(pages, 2);
```

```c
// __get_free_pages 直接返回虚拟地址
unsigned long addr = __get_free_pages(GFP_KERNEL, 0); // 单页
if (!addr) return -ENOMEM;
// 使用 (void *)addr ...
free_pages(addr, 0);
```

## SLUB Allocator

SLUB 替代了早期的 SLAB 分配器（Linux 2.6 引入 SLUB，当前为默认），用于管理**内核对象的缓存分配**，如 `task_struct`、`inode`、`dentry` 等频繁分配释放的小对象。

### 设计思想

SLUB 将 Buddy System 分配的连续页（一个 slab）划分为多个等大小的对象：

```
┌───────────────────────────────────────┐
│          Buddy 分配的连续页                │
│  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐  │
│  │o1│o2│o3│o4│o5│o6│o7│o8│o9│o10│  │  ← 等大小对象
│  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘  │
│  空闲对象链表 (freelist) ──────────→     │
└───────────────────────────────────────┘
```

核心特点：

* **每个 CPU 缓存** (per-CPU slab)：无锁分配热对象
* **每个 Node 缓存** (per-Node partial slab)：从其他 CPU 回收的部分空闲 slab
* **无元数据**：相比 SLAB，SLUB 不需要在每个对象上存储管理元数据，减少内存开销

### kmem_cache 操作

```c
// 1. 创建缓存
struct kmem_cache *my_cache = kmem_cache_create(
    "my_object",        // 名称（/proc/slabinfo 可见）
    sizeof(struct my_obj), // 对象大小
    0,                  // 对齐（0 = 自然对齐）
    SLAB_HWCACHE_ALIGN, // flags
    NULL                // 构造函数（可选）
);

// 2. 分配对象
struct my_obj *obj = kmem_cache_alloc(my_cache, GFP_KERNEL);

// 3. 释放对象
kmem_cache_free(my_cache, obj);

// 4. 销毁缓存
kmem_cache_destroy(my_cache);
```

### kmalloc 实现

`kmalloc` 基于通用缓存 (`kmalloc-32`, `kmalloc-64`, …, `kmalloc-8M`) 实现，每个缓存对应特定大小范围：

```c
// kmalloc 内部使用 kmem_cache 的通用缓存
void *p = kmalloc(128, GFP_KERNEL);  // 从 kmalloc-128 缓存分配
kfree(p);                            // 从地址反查 kmem_cache 并释放
```

### kmalloc vs vmalloc

| 特性 | kmalloc | vmalloc |
|------|---------|---------|
| 物理连续性 | **物理连续** | 虚拟连续，物理可能不连续 |
| 分配大小 | 典型 ≤ 4 MB | 适合大块分配 |
| 性能 | 快（直接 SLUB/Buddy） | 较慢（需建立页表映射） |
| 适用场景 | 驱动 DMA 缓冲区、内核对象 | 大块内存、模块加载 |
| 是否可睡眠 | 取决于 GFP flag | 是（会睡眠） |
| 最大限制 | `MAX_ORDER` (通常 4 MB) | 无硬限制（受 vmalloc 区大小限制） |

```c
#include <linux/vmalloc.h>

// kmalloc：物理连续，适合 DMA
void *dma_buf = kmalloc(4096, GFP_KERNEL | GFP_DMA);
// ... 使用 ...
kfree(dma_buf);

// vmalloc：虚拟连续，物理可能分散，适合大块
void *large_buf = vmalloc(10 * 1024 * 1024); // 10 MB
if (!large_buf) return -ENOMEM;
// 使用 large_buf ...
vfree(large_buf);
```

### 查看 slab 使用情况

```bash
# 每个 kmem_cache 的使用统计
cat /proc/slabinfo

# slabtop 动态查看（类似 top）
slabtop -o
```

## 内存分配器选择指南

| 场景 | 推荐分配器 |
|------|-----------|
| 驱动小对象 (< 4 MB，需物理连续) | `kmalloc` |
| 驱动 DMA 缓冲区 | `kmalloc(GFP_DMA)` 或 `__get_free_pages` |
| 大块内存 (> 4 MB) | `vmalloc` |
| 频繁分配/释放的对象 | `kmem_cache_create` + `kmem_cache_alloc` |
| 单个物理页 | `alloc_page` / `__get_free_page` |
| 用户进程匿名页 | `alloc_pages(GFP_HIGHUSER)` |
| 内核模块加载 | `vmalloc`（模块区） |
