随着项目规模增长，源码按模块分目录存放是必然选择。Makefile 管理多级目录主要有两种范式：递归 make 和非递归 make。

## 范式对比

| | 递归 make | 非递归 make |
|------|-----------|--------------|
| 方式 | 每个子目录有独立 Makefile，顶层逐级 `$(MAKE) -C` | 一个顶层 Makefile，通过 include 引入子目录片段 |
| 依赖图 | 不完整，每级只看到本级 | 全局依赖图，make 一次解析 |
| 并行 | 需要 `make -j` 手动传递，容易出错 | 天然支持 `make -j`，依赖正确 |
| 增量编译 | 可能在不需要时递归进入子目录 | 仅在依赖变化时重新编译 |
| 复杂度 | 子目录 Makefile 可独立测试 | 需小心变量命名和路径处理 |
| 适用 | 子模块完全独立、三方库 | 单一项目的多模块工程 |

Peter Miller 1997 年的经典论文 *Recursive Make Considered Harmful* 系统阐述了递归 make 的根本缺陷：make 无法看到完整依赖图，导致不必要的重新编译和错误的并行执行顺序。现代实践倾向非递归。

## 示例项目

```
project/
├── Makefile              # 顶层 Makefile
├── mk/                   # 共享 Makefile 片段
│   ├── common.mk
│   └── rules.mk
├── src/
│   ├── main/
│   │   ├── module.mk     # 本目录构建片段
│   │   └── main.c
│   ├── libfoo/
│   │   ├── module.mk
│   │   ├── foo.c
│   │   └── foo.h
│   └── libbar/
│       ├── module.mk
│       ├── bar.c
│       └── bar.h
├── include/
│   ├── foo.h
│   └── bar.h
├── build/                # 构建输出
└── bin/                  # 最终产物
```

## 递归 make（传统方式）

```makefile
# 顶层 Makefile
SUBDIRS = src/libfoo src/libbar src/main

.PHONY: all clean $(SUBDIRS)

all: $(SUBDIRS)

$(SUBDIRS):
	$(MAKE) -C $@ $(MAKECMDGOALS)

clean:
	for dir in $(SUBDIRS); do $(MAKE) -C $$dir clean; done
```

每个子目录维护独立的 Makefile：

```makefile
# src/libfoo/Makefile
CC = gcc
CFLAGS = -I../../include -Wall -g

libfoo.a: foo.o
	ar rcs $@ $^
```

**递归 make 的典型问题**：

```makefile
# 依赖 libfoo.a，但 make 不知道 -j 下 libfoo 和 main 的构建顺序
src/main/Makefile:
main: main.o ../libfoo/libfoo.a
```

顶层 Makefile 不知道子目录间的依赖关系。解决方式是手动声明顺序依赖：

```makefile
src/main: src/libfoo src/libbar    # 强制先构建 lib，但浪费了真正的并行机会
```

## 非递归 make（推荐）

核心思路：一个顶层 Makefile + 每个子目录提供 `module.mk` 描述本目录的源文件和编译选项，顶层汇总后统一构建。

```makefile
# 顶层 Makefile
ROOT := $(CURDIR)
BUILD_DIR := $(ROOT)/build
BIN_DIR := $(ROOT)/bin

CC := gcc
CFLAGS := -Wall -Wextra -std=c11
INCLUDES := -I$(ROOT)/include

# 收集所有模块
MODULES := src/libfoo src/libbar src/main

# 引入各模块定义
include $(foreach m,$(MODULES),$(m)/module.mk)

# 汇总所有目标
ALL_OBJS := $(addprefix $(BUILD_DIR)/,$(OBJS))
TARGET := $(BIN_DIR)/program

.PHONY: all clean

all: $(TARGET)

$(TARGET): $(ALL_OBJS)
	@mkdir -p $(@D)
	$(CC) $(LDFLAGS) -o $@ $^ $(LDLIBS)

$(BUILD_DIR)/%.o: $(ROOT)/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) $(INCLUDES) -c $< -o $@
	@echo "  CC  $<"

clean:
	rm -rf $(BUILD_DIR) $(BIN_DIR)
```

**子目录 `module.mk`** 只定义变量，不写规则：

```makefile
# src/libfoo/module.mk
# 追加本模块的源文件和选项（注意用 := 避免无限递归）
SRCS_libfoo := src/libfoo/foo.c src/libfoo/foo_utils.c
OBJS += $(SRCS_libfoo:.c=.o)
CFLAGS += -Isrc/libfoo       # 模块私有头文件
```

```makefile
# src/main/module.mk
SRCS_main := src/main/main.c
OBJS += $(SRCS_main:.c=.o)
```

**用 foreach/eval 批量生成规则模板**：

```makefile
# mk/rules.mk — 共享编译规则
define COMPILE_rule
$(BUILD_DIR)/$(1)/%.o: $(ROOT)/$(1)/%.c
	@mkdir -p $$(@D)
	$$(CC) $$(CFLAGS) $$(INCLUDES) -c $$< -o $$@
endef

$(foreach mod,$(MODULES),$(eval $(call COMPILE_rule,$(mod))))
```

## 自动依赖生成

非递归 make 下为每个源文件生成 `.d` 依赖文件（记录 `#include` 的头文件）：

```makefile
# 依赖文件存放目录
DEP_DIR := $(BUILD_DIR)/dep

# 编译时生成 .d 文件
$(BUILD_DIR)/%.o: $(ROOT)/%.c
	@mkdir -p $(@D) $(DEP_DIR)/$(*D)
	$(CC) $(CFLAGS) $(INCLUDES) -MMD -MF $(DEP_DIR)/$*.d -c $< -o $@

# 引入所有生成的依赖文件（不存在时报错不中断）
DEP_FILES := $(patsubst $(ROOT)/%.c,$(DEP_DIR)/%.d,$(ALL_SRCS))
-include $(DEP_FILES)
```

`-MMD` 生成仅含用户头文件的依赖，`-MD` 含系统头文件。`-MF` 指定输出路径，`-MP` 为每个依赖添加空规则防止头文件删除后报错。

## vpath / VPATH

控制 make 在哪些目录下搜索依赖和规则：

```makefile
# VPATH 是 make 内置变量，冒号分隔
VPATH = src:include:lib

# vpath 是指令，支持模式匹配
vpath %.c src
vpath %.h include
vpath %.c src/libfoo
```

非递归 make 中通常不需要 vpath——直接用完整路径（如 `$(ROOT)/src/libfoo/foo.c`）更清晰。

## 编译目标分离（Debug / Release）

```makefile
# 顶层 Makefile
BUILD_TYPE ?= debug

ifeq ($(BUILD_TYPE), debug)
    CFLAGS += -g -O0 -DDEBUG
    BUILD_DIR := $(ROOT)/build/debug
else ifeq ($(BUILD_TYPE), release)
    CFLAGS += -O2 -DNDEBUG
    BUILD_DIR := $(ROOT)/build/release
else
    $(error Unknown BUILD_TYPE: $(BUILD_TYPE))
endif

# 使用
# make BUILD_TYPE=debug
# make BUILD_TYPE=release
```

不同构建类型的输出隔离到不同目录，切换时不需 `make clean`。

## 第三方库集成

```makefile
# 子目录引入
THIRD_PARTY := $(ROOT)/third_party
include $(THIRD_PARTY)/zlib/module.mk
include $(THIRD_PARTY)/openssl/module.mk

# pkg-config 方式
CFLAGS += $(shell pkg-config --cflags zlib)
LDLIBS += $(shell pkg-config --libs zlib)
```

## 最佳实践

* 优先非递归 make，构建大规模项目时差异显著
* `module.mk` 只定义变量，不写规则——所有规则在顶层或共享片段中统一定义
* 输出到独立 `build/` 目录，源目录保持干净
* 子模块用 `:=` 赋值给带前缀的变量（如 `SRCS_libfoo`），避免命名冲突
* 始终启用自动依赖（`-MMD` + `-MF`），头文件变更时自动触发重新编译
* 用 `$(MAKECMDGOALS)` 判断目标，避免伪目标进入子 make
* 用 `.ONESHELL`（GNU Make 4.X+）让规则在单个 Shell 中执行，免去续行符 `\` 的困扰
