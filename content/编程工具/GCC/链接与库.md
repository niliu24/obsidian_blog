> GCC 的链接阶段将多个目标文件（`.o`）和库文件（`.a` / `.so`）合并为可执行文件或共享库。理解静态库与动态库的原理、创建方法和常见链接错误，是 C/C++ 开发的基本功。

## 静态库 (`.a`)

静态库本质上是多个 `.o` 文件的归档包，链接时将需要的代码直接复制进最终可执行文件。

### 创建和使用

```c
// math_ops.c
int add(int a, int b) { return a + b; }
int mul(int a, int b) { return a * b; }

// main.c
#include <stdio.h>
int add(int, int);
int mul(int, int);

int main() {
    printf("3 + 4 = %d\n", add(3, 4));
    printf("3 * 4 = %d\n", mul(3, 4));
    return 0;
}
```

```bash
# 1. 编译目标文件
gcc -c -O2 math_ops.c -o math_ops.o

# 2. 打包为静态库
ar rcs libmathops.a math_ops.o

# 3. 查看库内容
ar t libmathops.a
nm libmathops.a          # 检查符号

# 4. 链接静态库
gcc main.c -L. -lmathops -o app_static

# 5. 确认链接方式
ldd app_static           # 输出 "not a dynamic executable"
file app_static          # "ELF 64-bit ... statically linked"
```

### ar 命令说明

| 选项 | 说明 |
|------|------|
| `r` | 替换/插入文件到归档 |
| `c` | 创建归档（不输出创建提示） |
| `s` | 创建索引（等效于单独执行 `ranlib`） |

`ar s` 等价于 `ranlib`——为归档内的符号建立索引，加快链接时符号查找。

### 静态库的链接行为

```
链接器处理过程（单遍扫描）:
  1. 按命令行从左到右扫描目标文件和库
  2. 维护一个"未解析符号"列表
  3. 遇到新 `.o` 或 `.a` 时，尝试用其中的符号定义解析"未解析符号"
  4. 扫描完整个命令行后，仍有未解析符号则报错 "undefined reference"
```

> **关键**: 库在命令行中的顺序重要！如果 `libA.a` 引用了 `libB.a` 中的符号，则 `-lA -lB` 顺序正确，`-lB -lA` 可能链接失败。可重复列出：`-lA -lB -lA`。

## 动态库 (`.so`)

动态库在编译时仅记录符号依赖，运行时由动态链接器 `ld-linux.so` 加载和解析。

### 创建和使用

```c
// 同一个 math_ops.c
int add(int a, int b) { return a + b; }
int mul(int a, int b) { return a * b; }
```

```bash
# 1. 编译 PIC 目标文件
gcc -c -fPIC -O2 math_ops.c -o math_ops.o

# 2. 创建共享库
gcc -shared -fPIC -Wl,-soname,libmathops.so.1 \
    -o libmathops.so.1.0 math_ops.o

# 3. 创建符号链接（soname → realname）
ln -sf libmathops.so.1.0 libmathops.so.1
ln -sf libmathops.so.1 libmathops.so

# 4. 编译时链接（记录依赖）
gcc main.c -L. -lmathops -o app_dynamic

# 5. 运行时需要找到库（详见下文路径搜索）
LD_LIBRARY_PATH=. ./app_dynamic
```

### soname 机制

```
libmathops.so.1.0   ← realname（包含完整版本号）
    ↑ 符号链接
libmathops.so.1     ← soname（仅 major 版本号）
    ↑ 符号链接
libmathops.so        ← linker name（编译时搜索用）
```

| 名称 | 格式 | 用途 |
|------|------|------|
| **realname** | `libfoo.so.X.Y.Z` | 实际库文件 |
| **soname** | `libfoo.so.X` | 嵌入到可执行文件中的依赖名，运行时匹配 |
| **linker name** | `libfoo.so` | 编译时 `-lfoo` 搜索的目标 |

### 运行时库依赖

```bash
# 查看可执行文件的依赖
ldd app_dynamic

# 查看库的 SONAME
objdump -p libmathops.so.1.0 | grep SONAME
readelf -d libmathops.so.1.0 | grep SONAME
```

## 库搜索路径

动态链接器的搜索顺序：

```
1. LD_LIBRARY_PATH 环境变量（冒号分隔）
2. /etc/ld.so.cache（由 ldconfig 生成）
3. 默认路径 /lib, /usr/lib
```

### 设置方法对比

| 方法 | 作用域 | 示例 |
|------|--------|------|
| `LD_LIBRARY_PATH` | 运行时环境变量 | `LD_LIBRARY_PATH=/opt/mylib ./app` |
| `rpath` | 编译时嵌入 ELF 的 `RPATH`/`RUNPATH` 段 | `-Wl,-rpath,/opt/mylib` |
| `ldconfig` | 系统级注册 | `sudo ldconfig /opt/mylib` |
| `/etc/ld.so.conf` | 系统级配置文件 | 编辑文件后运行 `ldconfig` |

### rpath vs LD_LIBRARY_PATH

```bash
# rpath 嵌入到可执行文件，不依赖环境变量
gcc main.c -L. -lmathops -Wl,-rpath,/opt/mylib -o app_rpath

# 查看嵌入的 rpath
readelf -d app_rpath | grep RPATH
readelf -d app_rpath | grep RUNPATH  # 若同时存在，RUNPATH 优先级低于 LD_LIBRARY_PATH
```

| 方法 | 优点 | 缺点 |
|------|------|------|
| rpath | 可执行文件自带搜索路径，用户无感 | 路径硬编码，不便迁移 |
| `LD_LIBRARY_PATH` | 临时覆盖，方便测试 | 环境变量污染，安全问题 |
| ldconfig | 全局生效 | 需要 root 权限 |

> **注意**: `RUNPATH`（`-Wl,--enable-new-dtags`）优先级低于 `LD_LIBRARY_PATH`，而旧的 `RPATH` 优先级高于 `LD_LIBRARY_PATH`。现代 GCC 默认使用 `RUNPATH`。

## 静态库 vs 动态库

| 对比维度 | 静态库 (`.a`) | 动态库 (`.so`) |
|----------|---------------|----------------|
| **文件大小** | 嵌入后膨胀可执行文件 | 可执行文件很小，库单独分发 |
| **启动速度** | 快（无加载重定位） | 稍慢（需 ld.so 加载和 PLT 修正） |
| **内存占用** | 每个进程独享，不共享物理内存 | 多个进程共享同一 `.so` 的物理页 |
| **更新方式** | 需重新链接全部依赖的可执行文件 | 替换 `.so` 文件即可（保持接口兼容） |
| **符号冲突** | 封装在可执行文件内，不影响外部 | 全局符号表可能被其他 `.so` 覆盖 |
| **部署** | 单文件，无运行时依赖 | 需确保目标系统有正确版本的 `.so` |
| **调试** | 调用栈清晰 | 需要 `.so` 的调试符号（`-g` 编译） |
| **安全性** | 不受 `LD_PRELOAD` 劫持 | 可通过 `LD_PRELOAD` 注入/覆写符号 |

## 高级链接特性

### 弱符号（Weak Symbol）

```c
// 弱定义：可被强定义覆盖
__attribute__((weak)) int weak_func() {
    return 0;
}

// 强定义：覆盖弱定义
int weak_func() {
    return 42;
}
```

```bash
# 查看符号强弱
nm libfoo.o | grep weak_func
# 'W' = 弱符号（未定义即用 0 填充）
# 'w' = 弱符号（未定义产生链接错误）
```

用途：为主函数提供默认实现，在库中可被应用程序覆盖。

### 符号可见性（Symbol Visibility）

```c
// foo.c
int internal_helper() { return 1; }                        // default: 对外可见

__attribute__((visibility("default")))
int public_api() { return internal_helper(); }             // 显式导出

__attribute__((visibility("hidden")))
int private_func() { return 0; }                           // 仅内部可见
```

```bash
# 编译时设置默认可见性
gcc -fvisibility=hidden -shared -o libfoo.so foo.c

# 查看导出符号
nm -D libfoo.so        # 动态符号表
```

使用 `-fvisibility=hidden` 配合 `__attribute__((visibility("default")))` 是最佳实践：

* 减少 `.so` 的导出符号数量，提高加载速度
* 避免符号冲突
* 编译器可对隐藏符号做更激进的优化

### 符号版本化（Symbol Versioning）

```bash
# 版本脚本 libfoo.map
VER_1.0 {
    global:
        public_api;
    local:
        *;
};

VER_2.0 {
    global:
        public_api;
        new_feature;
} VER_1.0;
```

```bash
gcc -Wl,--version-script,libfoo.map -shared -o libfoo.so.2.0 foo.c
```

### 函数拦截（LD_PRELOAD）

`LD_PRELOAD` 强制在程序启动时先加载指定 `.so`，其符号会覆盖之后加载的所有库：

```c
// mymalloc.c
#define _GNU_SOURCE
#include <dlfcn.h>
#include <stdio.h>
#include <stdlib.h>

void *malloc(size_t size) {
    static void *(*real_malloc)(size_t) = NULL;
    if (!real_malloc) real_malloc = dlsym(RTLD_NEXT, "malloc");
    void *ptr = real_malloc(size);
    printf("malloc(%zu) = %p\n", size, ptr);
    return ptr;
}
```

```bash
gcc -shared -fPIC -ldl mymalloc.c -o mymalloc.so
LD_PRELOAD=./mymalloc.so ./app   # 每次 malloc 都会打印
```

用途：内存泄漏检测、性能分析、沙箱行为修改。

### 链接器脚本基础

链接器脚本（linker script）控制 ELF 的内存布局：

```bash
# 查看默认链接器脚本
ld --verbose

# 使用自定义脚本
gcc -Wl,-T,custom.ld -o app main.o
```

常见场景：

* 嵌入式裸机程序的内存映射
* 指定 `.text`、`.data`、`.bss` 在特定地址
* 合并或移除特定段

## 常见链接错误

### 1. undefined reference（未定义引用）

**原因**: 链接器找不到某个符号的定义。

```bash
# 错误示例
gcc main.c -o app
# /usr/bin/ld: /tmp/ccxxx.o: undefined reference to symbol 'add'

# 解决方法：提供缺失的库
gcc main.c -L. -lmathops -o app
```

常见场景：

* 忘记链接库 (`-lm` 忘记 `#include <math.h>`)
* 库顺序错误（被依赖的库放后面）
* C 和 C++ 混合编译时缺少 `extern "C"`

### 2. multiple definition（多重定义）

**原因**: 同一符号在多个目标文件中定义。

```bash
# 两个文件都定义了全局变量 int global_var;
gcc a.o b.o -o app
# multiple definition of `global_var'
```

解决方法：

* 使用 `static` 限制文件作用域
* 使用 `-Wl,--allow-multiple-definition`（取第一个定义，不推荐）
* 声明为 `extern`，只在**一个**文件中定义

### 3. cannot open shared object file（运行时找不到库）

```bash
# 编译成功，但运行时：
./app
# error while loading shared libraries: libmathops.so.1: cannot open shared object file

# 解决方法
LD_LIBRARY_PATH=. ./app          # 临时
export LD_LIBRARY_PATH=$PWD      # 当前会话
sudo ldconfig /path/to/lib       # 系统级
```

### 4. 符号截断（Symbol truncation）

```bash
# 某些平台符号名长度受限
nm foo.o
# warning: symbol 'very_long_function_name_exceeding_limit' truncated
```

## 链接实战

```bash
# 完整构建：静态库
gcc -c -O2 -fPIC math_ops.c
ar rcs libmathops.a math_ops.o
gcc main.c -L. -lmathops -static -o app_static

# 完整构建：动态库
gcc -c -O2 -fPIC math_ops.c
gcc -shared -Wl,-soname,libmathops.so.1 -o libmathops.so.1.0 math_ops.o
ln -sf libmathops.so.1.0 libmathops.so.1
ln -sf libmathops.so.1 libmathops.so
gcc main.c -L. -lmathops -Wl,-rpath,$PWD -o app_dynamic

# 验证
file app_static app_dynamic
ldd app_dynamic
nm -D app_dynamic | grep add
```
