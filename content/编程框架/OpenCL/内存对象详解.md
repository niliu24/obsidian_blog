OpenCL 有三类内存对象：**Buffer**（线性内存）、**Image**（带格式的多维纹理）、**Pipe**（生产者 - 消费者队列，OpenCL 2.0+）。它们都是 `cl_mem` 类型，通过引用计数管理生命周期。

## Buffer

Buffer 是设备端一维连续字节序列。最通用、最灵活的内存对象。

```c
cl_mem clCreateBuffer(cl_context context, cl_mem_flags flags,
                      size_t size, void *host_ptr, cl_int *errcode_ret);
```

每个 buffer 对象与一个 context 绑定（而非 device），同一 context 内的多个 device 可共享，由运行时负责设备间的数据迁移或一致性。

```c
#define N 1024
float a[N], b[N], c[N];

// 创建时拷贝数据
cl_mem d_a = clCreateBuffer(context, CL_MEM_READ_ONLY | CL_MEM_COPY_HOST_PTR,
                            sizeof(float) * N, a, &err);

// 仅分配，不拷贝
cl_mem d_b = clCreateBuffer(context, CL_MEM_READ_WRITE,
                            sizeof(float) * N, NULL, &err);

// 零拷贝：使用 CL_MEM_USE_HOST_PTR，需保证 host_ptr 在 buffer 存活期内有效
cl_mem d_c = clCreateBuffer(context, CL_MEM_WRITE_ONLY | CL_MEM_USE_HOST_PTR,
                            sizeof(float) * N, c, &err);
```

### 矩形区域传输

针对 2D/3D 数据的子区域传输，使用 `clEnqueueReadBufferRect` / `clEnqueueWriteBufferRect`：

```c
cl_int clEnqueueReadBufferRect(
    cl_command_queue queue, cl_mem buffer, cl_bool blocking,
    const size_t buffer_origin[3],   // buffer 内起始坐标 (x,y,z)
    const size_t host_origin[3],     // host 内存起始坐标 (x,y,z)
    const size_t region[3],          // 区域大小 (width, height, depth)
    size_t buffer_row_pitch,         // buffer 中每行字节数
    size_t buffer_slice_pitch,       // buffer 中每个 2D 面的字节数
    size_t host_row_pitch,           // host 内存中每行字节数
    size_t host_slice_pitch,         // host 内存中每个 2D 面的字节数
    void *ptr, cl_uint num_events, const cl_event *wait_list, cl_event *event);
```

#### 参数语义详解

核心概念：buffer 被当作一个 **三维逻辑数组**（x=字节偏移，y=行号，z=面号），以 row-major 存储。矩形传输从此数组中切出一个子长方体。

```
                    buffer_origin.x (字节)
                    │
                    ▼
┌──────────────────────────────────────────────┐
│  ┌──────────────────────┐                   │
│  │  ░░░░░░░░░░░░░░░░░░  │ ← region[0]      │ slice_pitch
│  │  ░░░  ROI 区域  ░░░  │   (width 字节)   │ (面间跨度)
│  │  ░░░░░░░░░░░░░░░░░░  │                   │
│  │  ░░░░░░░░░░░░░░░░░░  │ region[1] 行     │
│  └──────────────────────┘                   │
│  padding / 下一面                            │
└──────────────────────────────────────────────┘
        │◄── row_pitch (行跨度) ──│
```

| 参数 | 单位 | 含义 | 传 0 时的默认值 |
|------|------|------|----------------|
| `buffer_origin[3]` | `(字节, 行, 面)` | buffer 中取数据的三维起始坐标 | - |
| `host_origin[3]` | `(字节, 行, 面)` | host 内存中写入/读取的三维起始坐标 | - |
| `region[0]` | 字节 | 每行拷贝的**实际数据**字节数 | - |
| `region[1]` | 行数 | 每个 2D 面包含的行数 | - |
| `region[2]` | 面数 | 2D 面的数量（1 表示单个 2D 平面） | - |
| `buffer_row_pitch` | 字节 | buffer 中**一行**占用的总字节数（含 padding） | `region[0]` |
| `buffer_slice_pitch` | 字节 | buffer 中**一个面**占用的总字节数（含 padding） | `region[1] * buffer_row_pitch` |
| `host_row_pitch` | 字节 | host 内存中一行的总字节数（含 padding） | `region[0]` |
| `host_slice_pitch` | 字节 | host 内存中一个面的总字节数（含 padding） | `region[1] * host_row_pitch` |

**关键点**：`row_pitch` 和 `slice_pitch` 描述的是**内存布局中的跨度**（stride），而 `region` 描述的是**实际有效数据**的尺寸。`row_pitch` 必须 ≥ `region[0]`，`slice_pitch` 必须 ≥ `region[1] * buffer_row_pitch`。大于时，多余部分为 padding，传输时被跳过。

#### 每一行的具体拷贝过程

```
内存中的一行（buffer_row_pitch 字节宽）:
│◄──── region[0] ────│◄── padding ──│
│ [实际拷贝的数据]      │  跳过        │
```

传输对每一行做同样的事：从当前行起始位置拷贝 `region[0]` 字节，然后跳跃到下一行起始（偏移 `row_pitch` 字节）。layer 之间同理——完成 `region[1]` 行后，偏移到下一面（偏移 `slice_pitch` 字节）。

#### 使用场景

**场景 1: ROI 提取 — 从大图中抠小图**

```c
// 2048×1024 的大 buffer 中，提取位于 (512, 256) 处的 256×128 子区域
size_t buffer_origin[] = {512 * sizeof(float), 256, 0};  // x=2048字节, y=256行
size_t host_origin[]   = {0, 0, 0};
size_t region[]        = {256 * sizeof(float), 128, 1};   // 宽 1024字节, 高 128行

clEnqueueReadBufferRect(queue, d_big, CL_TRUE,
    buffer_origin, host_origin, region,
    2048 * sizeof(float), 0,   // buffer 每行 2048 个 float, slice_pitch 自动计算
    0, 0,                      // host 端紧密排列
    host_sub_img, 0, NULL, NULL);
```

**场景 2: 带 padding 的行对齐 — GPU 纹理/缓存行对齐**

```c
// GPU 要求行对齐到 128 字节 (texture row alignment)
// 实际图像宽 250 float (1000字节)，padding 到 1024 字节 (256 float)
size_t row_pitch = 256 * sizeof(float);  // 1024 字节对齐行
size_t region[]  = {250 * sizeof(float), height, 1};  // 有效数据仅 1000 字节/行

clEnqueueWriteBufferRect(queue, d_tex, CL_TRUE,
    (size_t[]){0,0,0}, (size_t[]){0,0,0}, region,
    row_pitch, 0,    // buffer 端每行 1024字节，拷贝时只取前 1000字节
    0, 0,            // host 端紧密排列（无 padding）
    host_tight_packed, 0, NULL, NULL);
```

**场景 3: 跨 buffer 子区域拷贝 — 无需 host 中转**

```c
// 将 buffer A 中 (32,64) 位置开始的 128×128 矩形拷贝到 buffer B 中 (0,0)
clEnqueueCopyBufferRect(queue,
    d_src, d_dst,
    (size_t[]){32*sizeof(float), 64, 0},   // src_origin
    (size_t[]){0, 0, 0},                    // dst_origin
    (size_t[]){128*sizeof(float), 128, 1},  // region
    src_row_pitch, 0,                       // src 行/面 pitch
    dst_row_pitch, 0,                       // dst 行/面 pitch
    0, NULL, NULL);
```

**场景 4: 3D 体数据 — 提取子体积块**

```c
// 256×256×256 的 3D 体数据，提取位于 (64,64,32) 的 32×32×16 子块
size_t buffer_origin[] = {64*sizeof(float), 64, 32};
size_t region[]        = {32*sizeof(float), 32, 16};

clEnqueueReadBufferRect(queue, d_volume, CL_TRUE,
    buffer_origin, (size_t[]){0,0,0}, region,
    256*sizeof(float),                          // row_pitch: 完整的一行
    256*sizeof(float) * 256,                    // slice_pitch: 完整的一个面
    0, 0,
    host_sub_volume, 0, NULL, NULL);
```

**场景 5: 图像通道分离 — 利用 host_origin 重排数据**

```c
// RGBA interleaved buffer 中提取 R 通道到独立 host buffer
// buffer 每像素 4 字节 (RGBA)，region[0]=1 每次只取 1 字节
// host_row_pitch = region[0] 使 host 端紧密排列 → 得到纯 R 通道数组
clEnqueueReadBufferRect(queue, d_rgba, CL_TRUE,
    (size_t[]){0, 0, 0},        // buffer_origin: 从 R 字节开始, 每次跳 4 字节取 1
    (size_t[]){0, 0, 0},
    (size_t[]){1, height, 1},   // region: 每行 1 字节, height 行
    4, 0,                       // buffer_row_pitch = 4 (跳过 GBA)
    0, 0,                       // host 端紧密排列
    host_r_channel, 0, NULL, NULL);
```

此场景虽然可以完成任务，但逐字节传输效率低。大量数据时应优先用 kernel 做通道重排。

#### row_pitch 和 slice_pitch 的约束总结

```
buffer_row_pitch  >= region[0]     (行跨度不小于实际数据宽)
buffer_slice_pitch >= region[1] * buffer_row_pitch  (面跨度不小于实际行数×行跨度)
host_row_pitch    >= region[0]
host_slice_pitch  >= region[1] * host_row_pitch
```

当 `row_pitch` = 0 时，OpenCL 假定数据**紧密排列**（即 `row_pitch = region[0]`）；当 `slice_pitch` = 0 时，假定 `slice_pitch = region[1] * row_pitch`。这为简单场景提供了便捷默认值。

### 缓冲区填充与复制

```c
// 用固定模式值填充 buffer（OpenCL 1.2+）
int pattern = 0;
clEnqueueFillBuffer(queue, d_a, &pattern, sizeof(int), 0, sizeof(int) * N, 0, NULL, NULL);

// 两个 device buffer 之间复制（不需要 host 中转）
clEnqueueCopyBuffer(queue, d_src, d_dst, 0, 0, sizeof(float) * N, 0, NULL, NULL);
```

`clEnqueueFillBuffer` 的 pattern 大小必须是 2 的幂且 ≤ 128 字节，按指定字节长度重复填充整个区域。

### 子 Buffer

从父 buffer 切分，共享底层内存，零额外分配：

```c
cl_buffer_region region = { .origin = 256, .size = 1024 };
cl_mem sub = clCreateSubBuffer(parent, CL_MEM_READ_WRITE,
                               CL_BUFFER_CREATE_TYPE_REGION, &region, &err);
```

子 buffer 和父 buffer 可独立使用，引用计数独立。父 buffer 释放后子 buffer 仍然有效，实际内存在最后一个引用释放时才回收。注意避免父子 buffer 之间的数据竞争——重叠区域同时读写结果不确定。

## Image

Image 是设备端带格式的多维数据对象，适合图像处理、采样、滤波。

```c
cl_mem clCreateImage2D(cl_context context, cl_mem_flags flags,
                       const cl_image_format *image_format,
                       size_t image_width, size_t image_height,
                       size_t image_row_pitch, void *host_ptr, cl_int *errcode_ret);

cl_mem clCreateImage3D(cl_context context, cl_mem_flags flags,
                       const cl_image_format *image_format,
                       size_t image_width, size_t image_height, size_t image_depth,
                       size_t image_row_pitch, size_t image_slice_pitch,
                       void *host_ptr, cl_int *errcode_ret);
```

### Buffer vs Image

| | Buffer | Image |
|------|--------|-------|
| 数据结构 | 一维字节序列 | 2D/3D 带格式纹理 |
| 访问方式 | 指针直接索引 | `read_imagef` / `write_imagef` 等内置函数 |
| 硬件支持 | 普通显存 | 利用纹理缓存和纹理单元（L1 之外的专用 cache） |
| 寻址 | 手动计算偏移 | 自动处理边界（clamp/repeat/mirror） |
| 采样 | 无 | 硬件双线性/三线性插值，几乎零额外开销 |
| 适用 | 通用数据、自定义结构体 | 图像、滤波、卷积、采样密集型计算 |

Images cannot be accessed via raw pointers in the kernel — you must use the built-in `read_image*` / `write_image*` functions. This restriction enables the hardware texture cache.

### Image Format

```c
cl_image_format fmt;
fmt.image_channel_order = CL_RGBA;   // 通道布局
fmt.image_channel_data_type = CL_UNORM_INT8;  // 每通道数据类型

// Kernel 端
__kernel void process_image(read_only image2d_t input,
                            write_only image2d_t output) {
    int x = get_global_id(0);
    int y = get_global_id(1);

    sampler_t sampler = CLK_NORMALIZED_COORDS_FALSE |
                        CLK_ADDRESS_CLAMP_TO_EDGE |
                        CLK_FILTER_NEAREST;

    float4 pixel = read_imagef(input, sampler, (int2)(x, y));
    pixel.xyz *= 0.5f;
    write_imagef(output, (int2)(x, y), pixel);
}
```

`read_imagef` 始终返回 `float4`；`read_imagei` 返回 `int4`；`read_imageui` 返回 `uint4`。即使图像格式是 `CL_UNORM_INT8`（GPU 内部存储为 8 位），硬件自动完成归一化（`0-255 → 0.0-1.0`），kernel 中看到已经是 `float4`，零额外开销。

## Pipe（OpenCL 2.0+）

Pipe 是 FIFO 队列结构，用于 kernel 之间的生产者 - 消费者通信，数据不出 device：

```c
cl_mem clCreatePipe(cl_context context, cl_mem_flags flags,
                    cl_uint pipe_packet_size, cl_uint pipe_max_packets,
                    const cl_pipe_properties *properties, cl_int *errcode_ret);
```

```c
// Kernel A（生产者）
__kernel void producer(write_only pipe int_pipe __write_only) {
    int data = compute();
    reserve_id_t rid = reserve_write_pipe(int_pipe, 1);   // 预约 1 个槽位
    if (is_valid_reserve_id(rid)) {
        write_pipe(int_pipe, rid, 0, &data);
        commit_write_pipe(int_pipe, rid);
    }
}

// Kernel B（消费者）
__kernel void consumer(read_only pipe int_pipe __read_only) {
    int data;
    reserve_id_t rid = reserve_read_pipe(int_pipe, 1);
    if (is_valid_reserve_id(rid)) {
        read_pipe(int_pipe, rid, 0, &data);
        commit_read_pipe(int_pipe, rid);
    }
    process(data);
}
```

Pipe 的视角与 Buffer/Image 完全不同——它是流式的。一个 packet 只有被完整写入并提交后才能被消费者读取。生产者和消费者必须分属不同的 kernel 调用（不可在同一个 kernel 中同时读写同一 pipe）。

## Memory Flags

所有内存对象共享的核心 flags：

| Flag | 含义 | 适用范围 |
|------|------|---------|
| `CL_MEM_READ_WRITE` | kernel 可读可写 | Buffer, Image |
| `CL_MEM_READ_ONLY` | kernel 只读 | Buffer, Image |
| `CL_MEM_WRITE_ONLY` | kernel 只写 | Buffer, Image |
| `CL_MEM_USE_HOST_PTR` | 直接使用 host 内存 | Buffer, Image |
| `CL_MEM_ALLOC_HOST_PTR` | 分配 host 可访问内存 | Buffer, Image |
| `CL_MEM_COPY_HOST_PTR` | 创建时拷贝数据 | Buffer, Image |
| `CL_MEM_HOST_READ_ONLY` | Host 只读 | Buffer, Image |
| `CL_MEM_HOST_WRITE_ONLY` | Host 只写 | Buffer, Image |
| `CL_MEM_HOST_NO_ACCESS` | Host 不可访问 | Buffer, Image |
| `CL_MEM_KERNEL_READ_AND_WRITE` | kernel 读写（Pipe 禁用） | Pipe |

`CL_MEM_READ_ONLY` / `CL_MEM_WRITE_ONLY` 不仅是一种声明（文档作用），更允许运行时将 buffer 放入更快的 device-local 内存而非 host-visible 区域——对分立的 GPU 显存而言这是显著的性能差异。

### Flags 底层实现机制

Memory flags 不是简单的位掩码开关，它们决定了驱动层的内存分配路径、GPU 页表映射、cache 策略和 DMA 行为。

#### 1. Access Qualifiers — 决定内存物理位置

```
         ┌──────────────────────────────────┐
         │         GPU Device Memory        │
         │  ┌────────────┐  ┌────────────┐  │
         │  │  _PRIVATE_ │  │ _CONSTANT_ │  │  ← CL_MEM_READ_ONLY 可放入
         │  │  (寄存器)   │  │  (constant │  │     constant cache
         │  │            │  │   cache)    │  │
         │  └────────────┘  └────────────┘  │
         │  ┌────────────────────────────┐  │
         │  │      Global VRAM           │  │  ← 所有 buffer 默认位置
         │  │   (GDDR / HBM / HBM2e)     │  │
         │  └────────────────────────────┘  │
         └───────────┬──────────────────────┘
                     │ PCIe BAR (256MB~)
         ┌───────────▼──────────────────────┐
         │       System RAM (Host)          │
         │  ┌────────────────────────────┐  │
         │  │   Pinned / Page-locked     │  │  ← CL_MEM_ALLOC_HOST_PTR
         │  │   (DMA 可直达)              │  │     CL_MEM_USE_HOST_PTR
         │  └────────────────────────────┘  │
         │  ┌────────────────────────────┐  │
         │  │   Pageable (可分页)         │  │
         │  └────────────────────────────┘  │
         └──────────────────────────────────┘
```

**`CL_MEM_READ_ONLY`**：

* 驱动可将 buffer 放入 GPU 的 **read-only data cache**（NVIDIA 的常量缓存/L1 只读路径），kernel 通过 `__global const*` + `__attribute__((const))` 或 `ldg`（NVIDIA PTX 的 load-global-cached）指令访存
* 在分立的 dGPU 上，驱动倾向于在 VRAM 中分配且**不建立 host→device 的反向 BAR 映射**，减少 MMU TLB 压力
* 某些实现会将该 buffer 标记为 **device-local + host-invisible**，使得 clEnqueueMapBuffer 时必须通过 staging buffer 拷贝

**`CL_MEM_WRITE_ONLY`**：

* 驱动可以**延迟分配**物理页——直到 kernel 首次写入时才真正提交物理内存
* 允许使用 GPU 的 **write-combining** 路径，多个 write 合并为一次 burst transaction
* Host 端读取此 buffer 是未定义行为（实际上会读到垃圾或触发 segfault）

**`CL_MEM_READ_WRITE`**：

* 最保守的分配策略，buffer 必须同时在 device 端可读写且 host 端可访问
* 在 dGPU 上需要通过 PCIe BAR 维持 host 可见窗口，开销最大

#### 2. Host Ptr Flags — 决定内存分配位置和拷贝时机

三类 host ptr flag 对应三种不同的分配策略：

| 策略 | GPU 显存 | Host 内存 | DMA 拷贝 |
|------|----------|-----------|----------|
| `CL_MEM_COPY_HOST_PTR` | **分配** | 临时使用 `host_ptr` 指向区域 | 创建时执行一次 |
| `CL_MEM_ALLOC_HOST_PTR` | 不分配 | **分配** pinned 内存 | GPU 通过 PCIe 直接访存 |
| `CL_MEM_USE_HOST_PTR` | 不分配 | **使用**用户传入的 `host_ptr` | 无，需 pin 用户内存 |

##### COPY_HOST_PTR — 标准路径

```
创建时:
  host_ptr → [malloc 的普通内存] ──DMA──→ [GPU VRAM 中的 buffer]
创建后:
  host_ptr 可立即释放，device 端独立持有副本
```

驱动内部调用链（以 NVIDIA 实现为例）：

1. `clCreateBuffer` → `cuMemAlloc`（在 VRAM 中分配）
2. 如果 `host_ptr != NULL` → `cuMemcpyHtoD`（同步 DMA，将 host 数据拷贝到 VRAM）
3. 返回的 `cl_mem` 仅管理 VRAM 端的存储

##### ALLOC_HOST_PTR — 零拷贝 / Pinned Memory

```
创建后:
  ┌─────────┐     PCIe BAR / Zero-copy     ┌──────────────────┐
  │   GPU   │ ←──────────────────────────→ │  Pinned System   │
  │   CU    │    每次 kernel 访存走 PCIe     │  RAM (Page-locked)│
  └─────────┘                              └──────────────────┘
```

* 调用 `cuMemAllocHost`（NVIDIA）或 `clGetMemObjectHostPtr` 获取主机地址
* 内存物理页被 **pin（锁定）**，OS 不会将其 swap 到磁盘，DMA 引擎可直接访问
* GPU 通过 PCIe bus-master 直接读/写这块内存，**不需要显式的 clEnqueueRead/WriteBuffer**
* **关键性能特征**：GPU 访存延迟 = PCIe 往返延迟（~几百 ns），带宽受 PCIe 限制（PCIe 4.0 x16 ≈ 32 GB/s），远低于 VRAM（~1 TB/s）。适合数据仅被 GPU 少量访问的场景

##### USE_HOST_PTR — 用户内存映射

```
用户分配的内存:
  float *data = malloc(N * sizeof(float));  // 普通可分页内存
  
clCreateBuffer(..., CL_MEM_USE_HOST_PTR, data, ...):
  1. 驱动调用 cuMemHostRegister(data, size, 0)  // pin 这片内存
  2. GPU MMU 建立该地址范围的页表映射
  3. GPU 通过 PCIe 直接读/写 data
  4. clReleaseMemObject → cuMemHostUnregister  // unpin
```

关键约束：

* `host_ptr` 在 buffer 存活期内必须有效且不能被 host 释放
* pin 操作本身有开销（OS 需要锁定所有涉及的物理页）
* 如果 `host_ptr` 未对齐到 4096 字节边界，驱动可能需要额外处理
* 适合已有大量 host 数据、不想通过拷贝传输的场景

#### 3. Host Access Flags — 优化 DMA 和 Cache 一致性

这三个 flag 是对分配策略的**精细调优**，告诉驱动 host 将如何访问 buffer，从而优化 DMA 引擎配置和 cache 一致性协议：

```
                Host 端                    Device 端
                ───────                    ─────────
HOST_NO_ACCESS:  ❌ 不可访问 ──DMA──→      ✅ VRAM 独享
                    不需要建立 BAR 映射
                    不需要 pin 内存
                    GPU 端 cache 无需考虑 host 可见性

HOST_READ_ONLY:   ✅ 只读 ──DMA──→         ✅ 可读写
                    优化方向：GPU→Host 的 DMA 传输
                    GPU 端 cache 行标记为 clean

HOST_WRITE_ONLY:  ✅ 只写 ──DMA──→         ✅ 可读写  
                    优化方向：Host→GPU 的 DMA 传输
                    GPU 端可跳过 cache 失效操作
```

这三个 flag 的具体硬件影响：

* **`CL_MEM_HOST_NO_ACCESS`**：驱动**不为该 buffer 建立 PCIe BAR 映射**。在 NVIDIA GPU 上，这意味着 buffer 完全驻留在 large-bar VRAM 或通过 `cudaMalloc` 分配的 device memory 中。Host 试图通过 clEnqueueMapBuffer 访问将触发**隐式 staging buffer 拷贝**（驱动分配临时 pinned memory → DMA 拷贝 → 映射给 host → Unmap 时拷回）。适合纯 kernel 计算的中间结果。
* **`CL_MEM_HOST_READ_ONLY`**：DMA 引擎方向设为 **Device→Host**（单向）。GPU cache 行在 kernel 写完后标记为 dirty，仅当 host 发起 Map 操作时才 flush。减少了维护双向一致性的开销。
* **`CL_MEM_HOST_WRITE_ONLY`**：DMA 方向设为 **Host→Device**（单向）。Host 写入不需要先从 device 读取，可以用 write-combining buffer 加速。`CL_MAP_WRITE_INVALIDATE_REGION` 与此 flag 配合使用效果最佳——跳过 device 端旧数据的读取。

#### 4. 分立的 GPU vs 集成 GPU 的实现差异

| 层面 | 分立的 GPU (dGPU) | 集成 GPU (iGPU, APU) |
|------|-------------------|---------------------|
| 物理内存 | VRAM 独立于系统 RAM | 共享同一物理内存（UMA） |
| `COPY_HOST_PTR` | DMA 拷贝到 VRAM | 可能退化为 memcpy 到另一片物理页 |
| `ALLOC_HOST_PTR` | 在系统 RAM 分配 pinned memory | 分配普通页，GPU 通过系统总线访问，真正的零拷贝 |
| `USE_HOST_PTR` | 需要 pin，频繁访问时 PCIe 是瓶颈 | 几乎零开销，仅建立页表映射 |
| `READ_ONLY` 加速效果 | 显著（放入专用常量缓存/纹理缓存，避免 PCIe 往返） | 有但不如 dGPU 明显（内存延迟差异小） |
| 一致性模型 | 显式同步（Map/Unmap 或 event） | 可能支持完全一致（fine-grained SVM） |

在集显上，`CL_MEM_ALLOC_HOST_PTR` 与 `CL_MEM_USE_HOST_PTR` 的性能差异很小——两者最终都指向系统 RAM，区别只是前者由驱动分配后者由用户分配。但在独显上，`ALLOC_HOST_PTR` 决定数据驻留在系统 RAM 端（GPU 每次访问都走 PCIe），而 `COPY_HOST_PTR` 将数据迁移到 VRAM（GPU 访问速度最快）。

#### 5. 常见的 Flag 组合与对应的底层行为

```c
// 组合 1: 纯 device 端计算中间结果
// → VRAM 分配, 无 BAR 映射, 无 pin, host 不可见
clCreateBuffer(ctx, CL_MEM_READ_WRITE | CL_MEM_HOST_NO_ACCESS, size, NULL, &err);

// 组合 2: Host 写入数据, Device 只读 (如权重/查找表)
// → VRAM 分配 + 创建时 DMA 拷贝, 之后 host 不再访问
clCreateBuffer(ctx, CL_MEM_READ_ONLY | CL_MEM_COPY_HOST_PTR | CL_MEM_HOST_NO_ACCESS,
               size, host_data, &err);

// 组合 3: 零拷贝映射, Host 写入, Device 读取
// → Pinned system RAM, GPU 通过 PCIe 读取, 真正的零拷贝
clCreateBuffer(ctx, CL_MEM_READ_ONLY | CL_MEM_ALLOC_HOST_PTR | CL_MEM_HOST_WRITE_ONLY,
               size, NULL, &err);

// 组合 4: Staging buffer 方案 — Device 计算 → host 读回结果
// → VRAM 分配用于计算, host 读回时通过隐式 staging buffer
clCreateBuffer(ctx, CL_MEM_READ_WRITE | CL_MEM_HOST_READ_ONLY, size, NULL, &err);

// 组合 5: SVM 替代方案 — 双向零拷贝
// → Pinned system RAM, GPU 和 CPU 均可读写, PCIe 双向
clCreateBuffer(ctx, CL_MEM_READ_WRITE | CL_MEM_ALLOC_HOST_PTR, size, NULL, &err);
```

组合选择的核心决策因素：**数据被谁访问、以什么频率访问、访问模式是读还是写**。错误的 flag 组合可能退化为隐式 staging buffer 拷贝（最坏情况下每次 kernel 执行前后各一次 DMA），性能差距可达数量级。

## 对象生命周期

所有内存对象通过引用计数管理：

```c
cl_mem buf = clCreateBuffer(...);     // refcount = 1
clRetainMemObject(buf);              // refcount = 2
clReleaseMemObject(buf);             // refcount = 1
clReleaseMemObject(buf);             // refcount = 0, 实际释放
```

当 refcount 归零时，底层 device 内存在所有排队命令完成后才真正回收——clReleaseMemObject 是非阻塞的，仅在引用计数语义上标记为抛弃，驱动负责安排延迟释放。

父子引用关系：

* 父 buffer 持有子 buffer 不增加引用计数——子 buffer 有自己的独立计数
* 父 buffer 释放后子 buffer 依然可用
* 上下文销毁时所有关联内存对象被视为 refcount=0

## SVM — Shared Virtual Memory（OpenCL 2.0+）

SVM 让 Host 和 Device 共享同一虚拟地址空间，kernel 可直接解引用 host 指针：

```c
// 粗粒度 SVM（最常用，一次映射整块 buffer）
float *data = (float *)clSVMAlloc(context, CL_MEM_READ_WRITE,
                                  sizeof(float) * N, 0);
// Host 端直接读写
data[0] = 3.14f;

// Kernel 端直接使用指针
clSetKernelArgSVMPointer(kernel, 0, data);
clEnqueueNDRangeKernel(...);

// 同步后 Host 读回
clEnqueueSVMMap(queue, CL_TRUE, CL_MAP_READ, data, sizeof(float)*N, 0, NULL, NULL);
printf("%f\n", data[0]);
clEnqueueSVMUnmap(queue, data, 0, NULL, NULL);
clSVMFree(context, data);
```

SVM 需要设备支持（`CL_DEVICE_SVM_COARSE_GRAIN_BUFFER`），且提供了对 atomics 的可选支持（`CL_DEVICE_SVM_FINE_GRAIN_BUFFER` + `CL_DEVICE_SVM_ATOMICS`）。与传统 `cl_mem` 的关键区别：kernel 中传的是裸指针（而非 `__global` 修饰的 buffer handle），Host 侧也不再需要 `clEnqueueRead/WriteBuffer`——映射/解除映射即可。

三种 SVM 粒度：

| 粒度 | 说明 | 同步方式 |
|------|------|---------|
| Coarse-grained | 整块 buffer 为单位 | Map/Unmap 或 kernel 完成后才可见 |
| Fine-grained | 字节级共享，无需显式同步 | 需 Atomics 保证一致性 |
| Fine-grained + Atomics | 字节级 + 原子操作 | 可全并发访问 |
